# Design engineer job description

A design engineer job description should read as a software role. The title alone will not do that. Mechanical, industrial, and chip jobs use the same words, and applicants from those fields will apply if the posting never mentions an interface, a design tool, or a codebase. Write the surface this person owns, the stack, and the kind of portfolio you will read.

## What belongs in a software design engineer job description?

A software design engineer job description names the surface, the stack, and a portfolio with something that runs. It says whether the seat implements an existing system or sets one. It publishes a yearly base range only when you have decided to publish it, in the currency you will actually pay.

### Template: software design engineer

```text
Design Engineer

[One sentence on the product.] You will own [the surface: the app UI, the design system, the marketing site]. The work is designing in code: prototypes, production interface, and the details that make the product feel finished.

What you will do
- Ship UI in the product, from a rough flow to a merged pull request.
- Prototype interactions in code when a static mock is not enough to decide.
- Build and maintain components, tokens, and documentation that other designers and engineers reuse.
- Pair with product design on the interaction and with engineering on how it lives in the existing app.
- Leave the interface accessible: keyboard, focus, contrast, and sensible empty and error states.

What you have done
- Production interface work in [React and TypeScript, or the stack you actually use]. CSS you are willing to own.
- A portfolio with something that runs, not only mockups. A design-system contribution, a prototype, or a shipped flow is enough to start the conversation.
- Comfort in [Figma, or the tool the team uses] and in the codebase.
- Judgment about visual and interaction quality, and the habit of writing it down so other people can reuse it.

Level
[Scope. Do they implement an existing system, or set it? How ambiguous is the problem? Is this a senior, staff, or unleveled req?]

Pay
Base salary: [yearly range you are willing to publish]. [Currency.] Equity, if you offer it, described separately from base.

Location
[Remote, and the countries you hire in. Or hybrid or on-site, and the city. Say which.]
```

Name the stack you use. Add SwiftUI, Framer, or WebGL only when the team uses them. [Framer jobs](/skills/framer) collide with carpentry search results when the posting never says the design tool. “Framer” next to “marketing site” or “React” is enough.

Publish the base range if you can. A yearly figure on the posting is what the salary page can cite, and it is what can appear as base salary on the job page. OTE and a hidden band cannot. Match the text on your apply page to the text you submit here. The hosted description is the one that gets marked up, and it has to be the real job.

Open examples of the title, with the employer’s own wording, are on [software design engineer jobs](/roles/design-engineer). Remote-only reqs are on [remote design engineer jobs](/remote).

## What belongs in a UX engineer job description?

A UX engineer job description uses the same bones and a sharper emphasis. The role is the high-fidelity prototype and the design-system API: interactions that are real enough to test, and components other designers can use without a custom one-off. Accessibility is part of the job, not a paragraph at the end.

See [what UX engineers do day to day](/guides/ux-engineer).

Ask for a portfolio with working prototypes. A case study that is only screenshots can be part of the story. It should not be the whole bar. Leave out a generic frontend ladder that never mentions design judgment. If you want a platform engineer, say frontend engineer. If you want a UX engineer, say what they will decide, not only what they will implement.

```text
UX Engineer

You will prototype and build the interface for [product]. The job is the interaction: states, motion, accessibility, and the component API the rest of the team ships on.

What you will do
- Build prototypes in code to decide an interaction before it is a committed feature.
- Implement production UI in [React, TypeScript, CSS] that matches the design and survives real content.
- Extend the design system: components, tokens, and the documentation a designer can follow.
- Review interface pull requests for quality, not only for correctness.

What you have done
- Shipped interface code and a prototype someone else could click through.
- Examples of accessibility treated as part of the design, not a follow-up ticket.
- Work next to product designers and frontend engineers, with a clear split of who decides what.
```

Live reqs are on [UX engineer jobs](/roles/ux-engineer). Pay that employers have published for the title is on [UX engineer salary](/salary/ux-engineer). A single principal posting is not a template salary. Use your own band.

For the difference between this seat and a product designer or a frontend engineer, see [what is a design engineer](/guides/what-is-a-design-engineer).

## How should a UI engineer posting differ?

A UI engineer posting should emphasize implementation quality: responsive layout, states, motion, and a component API other people can predict. Design judgment stays in the description. A generic frontend ladder, with no sentence about the interface, will miss the people who want this seat.

“UI developer jobs” and [UI engineer jobs](/roles/ui-engineer) are the same cluster on this board. Use that page when the posting says UI developer.

## How should a design technologist posting differ?

A design technologist posting is the bridge inside a design org: prototypes engineering can adopt, and the translation between a design file and a component. Say whether the person writes production code or stops at the prototype. A design systems engineer owns tokens and components across products. Those are different seats.

See [design technologist jobs](/roles/design-technologist). Both the production-code seat and the prototype-only seat are real jobs. They are not the same job.

The [design technologist role](/guides/design-technologist) guide defines the title and how it compares with a design engineer.

A design systems engineer owns tokens, documentation, and components that have to work in more than one product or platform. See [design systems engineer jobs](/roles/design-systems-engineer). “Design system jobs” belongs in this description. Write the platforms (web, iOS, and so on) and whether the person sets the system or implements a piece of it.

The [design systems engineer guide](/guides/design-systems-engineer) covers the skills and posted pay for the role.

Creative technologist postings lean toward campaign, brand, or real-time visual work. Link them to [creative technologist jobs](/roles/creative-technologist) when that is the seat, instead of stretching “design engineer” over a WebGL role the team will not recognize.

## Which lines attract the wrong applicants?

The lines that attract the wrong applicants are a title with no software qualifier, a tool list of CAD or FPGA, a frontend ladder with no interface judgment, and a hidden salary on a role you want filled quickly. Mechanical and hardware candidates read the shared title and stop there unless the first paragraph names an interface.

“Design engineer” with no software qualifier in the first paragraph. Applicants from mechanical and hardware search will read the title and stop.

A tool list that is SolidWorks, CAD, PCB, or FPGA. That is a different profession, and this board does not list it.

A requirements list copied from a generic frontend ladder, with no sentence about interface quality. You will get strong engineers who do not want this job, and miss the people who do.

An unpublished salary on a role you are trying to fill quickly. You can still post it. You should expect the [salary page](/salary) to ignore it, because there is nothing to cite.

## What should you check before you post?

Before you post, read the description once as a mechanical engineer would. If it still sounds like their job, add the stack and the surface. The text you submit is the text candidates see, and it is the text on the job page. Match it to the apply page.
